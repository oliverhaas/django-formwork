# Installation

Four steps: install the package, configure Django, install the icons, build the CSS. The optional htmx/Alpine.js setup for the dynamic widgets comes last.

## 1. Install the package

```bash
pip install django-formwork
```

Or with uv:

```bash
uv add django-formwork
```

## 2. Configure Django

Add `django_iconx` (a dependency that manages the icon set) and `django_formwork` to your installed apps, set the form renderer, and make sure you have a project-level static directory:

```python
# settings.py
INSTALLED_APPS = [
    ...,
    "django.contrib.staticfiles",
    "django_iconx",
    "django_formwork",
]

# Makes ALL forms use formwork templates automatically
FORM_RENDERER = "django_formwork.FormworkRenderer"

STATICFILES_DIRS = [BASE_DIR / "static"]
```

`django_iconx` must be in `INSTALLED_APPS` for the next step to work. `STATICFILES_DIRS` tells the icon install where to put the downloaded files and lets Django serve them.

## 3. Install the icons

Formwork's widgets use [Lucide](https://lucide.dev/) icons, fetched at setup time rather than bundled. Run:

```bash
python manage.py formwork install
```

This does two things:

1. Downloads the Lucide SVGs (via django-iconx) into `<first STATICFILES_DIRS entry>/icons/lucide/`.
2. Generates `iconx/icons.css` in your static directory, with one CSS class per icon pointing at the served SVGs.

The command is idempotent; rerunning it re-downloads and regenerates in place. Both output directories (`static/icons/` and `static/iconx/`) are generated artifacts: gitignore them and run `formwork install` in CI and on fresh checkouts, or commit them if you prefer vendoring.

### Command reference: `formwork install`

```
python manage.py formwork install [--output DIR]
```

- `--output DIR`: directory to write the generated CSS into (the file lands at `DIR/iconx/icons.css`). By default the command resolves your project static directory: the first entry of `STATICFILES_DIRS` if set, otherwise `BASE_DIR/static`. Use `--output` when your CSS build inputs live elsewhere.

Notes:

- The icon SVGs always download into the first `STATICFILES_DIRS` entry (django-iconx behavior); `--output` only moves the generated CSS.
- If `STATICFILES_DIRS` is not set, the command falls back to `BASE_DIR/static` and warns you: add that directory to `STATICFILES_DIRS`, or Django will not serve the icons.
- If neither `STATICFILES_DIRS` nor `BASE_DIR` is available in your settings, the command aborts with an error.

## 4. Build the CSS

Formwork uses [DaisyUI](https://daisyui.com/) 5 for component styling and [Tailwind CSS](https://tailwindcss.com/) 4+ for the build step. Formwork ships `formwork.css`, the Tailwind source: it contains `@apply` directives and `@import "tailwindcss"` itself, so it has to be processed by the Tailwind CLI or PostCSS plugin, and you must not import Tailwind or DaisyUI a second time next to it.

Install the build tools:

```bash
npm install -D tailwindcss @tailwindcss/cli daisyui@5
```

Create your Tailwind input (say `app.css` in your project root):

```css
/* Formwork's Tailwind source (already includes Tailwind + the DaisyUI plugin). */
@import "path/to/site-packages/django_formwork/static/formwork/formwork.css";

/* The icon classes generated by `manage.py formwork install` (step 3). */
@import "./static/iconx/icons.css";

/* Tell Tailwind to scan the formwork package AND your own templates. */
@source "path/to/site-packages/django_formwork/";
@source "./templates/";
```

The `@source` line for the package directory is required. Tailwind 4 only emits utility classes it finds in scanned sources, and formwork's widget templates and Python widget defaults reference classes of their own (the dropdown option layout, `tooltip-bottom` on error tooltips, `mask-star-2` on `Rating`, and so on). Without that `@source`, Tailwind tree-shakes those classes out and the widgets render unstyled.

To find the site-packages path for the import and `@source` lines:

```bash
python -c "import django_formwork; print(django_formwork.__path__[0])"
```

Then build:

```bash
npx @tailwindcss/cli -i app.css -o static/dist.css
```

And link the built file in your base template:

```html
{% load static %}
<link rel="stylesheet" href="{% static 'dist.css' %}">
```

The `examples/simple` app in the repository is a working copy of exactly this setup.

### DaisyUI version

Formwork requires **DaisyUI 5.x**. DaisyUI 4 and earlier use a different component API and are not compatible. Within the DaisyUI 5 series, formwork is tested against the latest stable release; any DaisyUI 5.x version should work.

## 5. htmx + Alpine.js (optional)

The dynamic widgets (server-side search, password reveal, combo boxes, validated textarea) depend on htmx 4 and Alpine.js. Load them yourself and then include the JS tag:

```html
<script src="https://cdn.jsdelivr.net/npm/htmx.org@4.0.0-beta3"></script>
<script defer src="https://cdn.jsdelivr.net/npm/alpinejs@3"></script>
{% load formwork %}
{% formwork_js %}
```

htmx 4 handles the server-side search and validation requests; its built-in `outerMorph` swap covers what idiomorph used to do in earlier versions. Alpine.js drives the client-side state of the dropdowns, password reveal, and drop zones. `{% formwork_js %}` loads `formwork.js` as an ES module, which in turn imports `formwork-core.js` (the htmx morph extension, dirty-field tracking, and native-validation disabling) plus each widget's Alpine.data component.

### JS loading paths

The `{% formwork_js %}` bundle is one tag and covers everything; that's the path most projects want. Two alternatives also work.

For per-form loading via Django's `Media`, use `{{ form.media }}` for the widget JS the form actually contains, and add `{% formwork_core_js %}` for the page-global core (morph, dirty-tracking, validation disabling). `SearchSelect`, `MultiSelect`, and `ComboBox` each declare a `Media` class pointing at their Alpine component file.

For bundler-driven loading, `import "/static/formwork/formwork.js"` from a vite, webpack, or esbuild entry. The bundler walks the chain and emits a single bundle; no template tag is needed.

ES modules are deduplicated by URL, so mixing tags is harmless. Combining `{% formwork_js %}` and `{% formwork_core_js %}` on the same page still executes the core only once.
